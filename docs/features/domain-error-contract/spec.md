> 🔵 **Generated by**: `[PLANNER · workflow-planner]`

## 1. Source Feature & Idea Diagnosis
* **`id`:** `domain-error-contract`
* **`area`:** `domain`
* **`depends_on`:** `["pragmatic-testing-cleanup"]` (`accepted` and merged into `feature/MM-02-design-system`)
* **`status`:** `accepted`
* **`module_topology`:** `Layer-Based (:domain, :usecases, :data, :app)`
* **Objective:** Replace `:data`'s legacy `CustomError` (`Either<CustomError, T>` / `ResultResponse<T>`) and `CustomErrorFlow` (`CustomErrorFlow?`) with a pure Kotlin `DomainError` sealed hierarchy and idiomatic `Result<out T, out E : DomainError>` contract owned by `:domain`, backed by structured-concurrency-safe `safeCall` / `safeSyncCall` helpers, typed `ErrorMapper` / `AuthErrorMapper` / `AndroidErrorMapper` exception mappers, and UI-layer `UiText` + `DomainError.toUiText()` localization.
* **Identified Ambiguities / Assumptions:**
  1. **Idiomatic Kotlin `Result<T, DomainError>` replaces Arrow `Either`**: A repository-wide `git grep "arrow\."` confirmed Arrow (`arrow-core`, `arrow-fx-coroutines`) is used exclusively for `Either<CustomError, T>` across 14 files that are already modified by this migration. Per `repository-pattern-governance`, replacing `Either` with `:domain`'s pure Kotlin `Result<out T, out E : DomainError>` eliminates third-party FP monad coupling, unifies `CustomError` and `CustomErrorFlow` into a single contract (`loadCityCurrentWeather` returns `Result<Unit, DomainError>` instead of nullable `CustomErrorFlow?`), and removes `libs.bundles.arrow` cleanly. Because `:data` and `:usecases` previously obtained `kotlinx.coroutines.flow.Flow` transitively through `arrow-fx-coroutines`, `kotlinx-coroutines-core` (`1.11.0`, matching existing `kotlinx-coroutines-test = "1.11.0"`) is declared explicitly in `gradle/libs.versions.toml`, `data/build.gradle.kts`, and `usecases/build.gradle.kts`.
  2. **Current Module Boundary Preservation (`WIP=1`)**: `:data` remains a pure JVM `java-library` module (holding repository/data-source interfaces, Retrofit service interface, `ErrorMapper`, `toDomainError()`, `safeCall`, `safeSyncCall`), while Android/Firebase/Room/Play Services implementations and `AndroidErrorMapper` / `AuthErrorMapper` remain in `:app`. Moving repository interfaces into `:domain` or converting `:data` to `com.android.library` is out of scope for this slice.
  3. **Zero Raw Exception Message Leakage**: `DomainError` subtypes carry no `Throwable` references and no raw exception strings (`DomainError.Unknown` is a `data object`; `DomainError.Network.ServerError(val code: Int)` carries only the HTTP status code). All user-facing error text resolves deterministically to localized `@StringRes` via `UiText` in `:app`.
* **Necessary Questions:** None — all requirements clarified.

## 2. Goal, Non-Goals & Acceptance Scenarios

### Goal
Establish a single, layer-pure, exhaustive `DomainError` hierarchy and `Result<T, DomainError>` contract in `:domain` so authentication, network/API, location/permission, local persistence, and unexpected failures map deterministically at the data boundary without ever leaking Android, Firebase, Room, Retrofit, or raw `Throwable` details into `:domain`, `:usecases`, ViewModels, or Compose UI.

### Non-Goals
* Do **NOT** redesign any Compose screen layouts, palettes, navigation graphs, or Design System (`Mm*`/`Fnd*`) components (owned by later visual/navigation overhaul slices; `app/src/test/snapshots/` 36 PNGs remain untouched).
* Do **NOT** modify Room database schema, entities, DAOs, or migrations (owned by `weather-condition-room-migration`).
* Do **NOT** convert `:data` from `java-library` to `com.android.library` or relocate repository interfaces into `:domain`.
* Do **NOT** alter `CityWeatherRepository.listOfCities: Flow<List<CityWeatherDomain>>` stream return type or `TemperatureCheckCoordinator`'s `TemperatureCheckOutcome` retry semantics.

### Job Story
When a network, authentication, location, permission, or local cache failure occurs in MeteoMartoCompose,
I want the data layer to translate the technical failure into a pure typed `DomainError` without swallowing coroutine cancellation,
so ViewModels remain framework-free and the UI displays deterministic, localized error messages without leaking raw exception details.

### Acceptance Scenarios

#### Scenario 1: Pure JVM & Retrofit/Network Exception Mapping via `safeCall`
* **Given** a suspending data operation wrapped in `safeCall` throws `SocketTimeoutException`, `IOException`, `HttpException` (`401`/`403` vs `500`/`404`), `JsonParseException`, `SecurityException`, `java.sql.SQLException`, or an unknown `RuntimeException`
* **When** `safeCall` executes and catches the exception
* **Then** it returns `Result.Error(...)` with the exact typed `DomainError` (`Network.Timeout`, `Network.NoInternet`, `Network.Unauthorized`, `Network.ServerError(code)`, `Network.Serialization`, `Location.PermissionDenied`, `Local.DatabaseError`, or `DomainError.Unknown`), never leaks raw exception strings, and rethrows `CancellationException` untouched.

#### Scenario 2: Firebase Auth, Remote Config, Location, and Room Exception Mapping
* **Given** `AccountServiceImpl`, `FirebaseRemoteConfigDataSourceImpl`, `LocationServerDataSourceImpl`, or `CityRoomDataSource` encounters an infrastructure failure (e.g., `FirebaseAuthWeakPasswordException`, `FirebaseAuthInvalidCredentialsException`, `FirebaseAuthUserCollisionException`, `FirebaseAuthInvalidUserException`, `FirebaseAuthException("ERROR_USER_TOKEN_EXPIRED")`, `FirebaseNetworkException`, `FirebaseRemoteConfigServerException`, `ApiException`, `SecurityException`, null location, missing city in Room, or `android.database.SQLException`)
* **When** the data source handles the operation through `AuthErrorMapper` / `AndroidErrorMapper` + `safeCall` / `safeSyncCall`
* **Then** it returns `Result.Error` with the corresponding `DomainError.Auth.*`, `DomainError.Network.*`, `DomainError.Location.*`, or `DomainError.Local.*` value (`Local.NotFound` when Room `getCityByName` returns `null`), and rethrows `CancellationException`.

#### Scenario 3: ViewModel Purity & Localized UI Error Presentation
* **Given** `LoginViewModel`, `SignUpViewModel`, `CityWeatherViewModel`, `FavoritesViewModel`, or `FavoritesDetailViewModel` receives a `Result.Error(domainError)` or local database flow failure
* **When** the ViewModel updates UI state/events and the Compose screen renders the error
* **Then** the ViewModel exposes only pure `DomainError` (with zero `:data` error imports, zero `R.string`, and zero Arrow `Either`), and the screen resolves `domainError.toUiText()` via `UiText.StringResource` to a localized `strings.xml` message.

#### Scenario 4: Zero Legacy `CustomError` / `CustomErrorFlow` / Arrow `Either` Artifacts
* **Given** the refactored repository across `:domain`, `:data`, `:usecases`, and `:app`
* **When** searching for `CustomError`, `CustomErrorFlow`, `ResultResponse`, `customTryCatch`, `customFlowTryCatch`, or `arrow.` in source and test code
* **Then** zero occurrences remain, `:domain` has zero external dependencies, and all `@compiler` verification gates pass cleanly.
