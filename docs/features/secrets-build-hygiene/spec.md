* **Objective:** Remove the hardcoded OpenWeather API key from `flavors.gradle` by adopting Google's `secrets-gradle-plugin` paired with a committed `local.defaults.properties` fallback file (`dependency-manager` Rule 12), align pure-JVM module Java/Kotlin targets (`:domain`, `:usecases`, `:data`) with `:app` on JDK/JVM 21 (`CONSTRAINTS.md` & `module-architecture-governance`), and fix outdated Design System trigger/Dokka paths in `.github/workflows/design-system-ci.yml` and `app/build.gradle.kts`.
* **Identified Ambiguities / Assumptions:**
  * **BuildConfig key name preserved (`API_KEY_VALUE`):** Keeping the property key named `API_KEY_VALUE` in `local.defaults.properties` (and locally overridden in git-ignored `local.properties`) allows `secrets-gradle-plugin` to generate `BuildConfig.API_KEY_VALUE` directly, keeping `APIKeyInterceptor.kt` functional with zero Kotlin churn.
  * **Non-secret constants stay in `flavors.gradle`:** `APP_ID_PARAM`, `API_WB_BASE`, `OPEN_WEATHER_ICON_URL`, and `app_name` are public non-secret configuration values and remain in `flavors.gradle` for both `pre` and `pro` flavors.
  * **Plugin version verified (`2.0.1`):** `com.google.android.libraries.mapsplatform.secrets-gradle-plugin` latest stable version is `2.0.1` (hosted on `google()`, already matched by `includeGroupByRegex("com\\.google.*")` in `settings.gradle.kts`).
  * **JVM target alignment (`21`):** `:app` already enforces `JavaVersion.VERSION_21` and `kotlin { jvmToolchain(21) }`, and `CONSTRAINTS.md` mandates JDK 21 locally (`jbr-21`) and in GitHub Actions CI. Aligning `:domain`, `:usecases`, and `:data` from JVM `17` to `21` eliminates mixed bytecode/toolchain targets across the repository.
  * **Configuration-cache verification risk:** `secrets-gradle-plugin:2.0.1` is known on some Gradle 8.x setups to surface configuration-cache or AGP variant warnings. Per `dependency-manager` Update Protocol §3 (Fail-and-Revert Policy), `workflow-implementer` must apply the plugin atomically and immediately verify both `assemblePreDebug` and the canonical `--configuration-cache` gate; if a plugin/AGP/Gradle incompatibility blocks the gate, roll back and report the exact log rather than adding forbidden imperative `java.util.Properties` I/O.
  * **Pre-existing `app/build.gradle.kts` gate blockers (Scope Amendment approved by developer):** During Stage 2 verification, two pre-existing `app/build.gradle.kts` regressions on `feature/MM-02-design-system` blocked the canonical `@compiler` gate: (a) missing `platform(libs.androidx.compose.bom)` in `androidTestImplementation` / `testImplementation` causing `:app:generatePreDebugAndroidTestLintModel` (`lintPreDebug`) to fail resolving `libs.androidx.ui.test.junit4`; and (b) hardcoded `roborazzi.test.record/compare/verify = "true"` in `testOptions.unitTests.all`, forcing `testPreDebugUnitTest` to run Roborazzi snapshot verification/recording instead of restricting visual regression to `:app:verifyRoborazziPreDebug`. Both are resolved within `secrets-build-hygiene` to restore a green canonical gate locally and in CI.
  * **Key rotation note (human follow-up):** Because a real OpenWeather API key previously lived in git history (`flavors.gradle`), rotating that key in the OpenWeather dashboard is recommended separately by the maintainer.

## 2. Goal, Non-Goals & Acceptance Scenarios

### Goal
Eliminate secret leakage in version-controlled Gradle scripts while keeping clean builds deterministic across CI runners and fresh developer clones where `local.properties` lacks an API key. At the same time, establish clean build hygiene across the repository by aligning all four Layer-Based modules on JDK/JVM 21 and pointing Design System CI triggers and Dokka filters at the real `ui/designsystem` package tree.

### Non-Goals
* Migrating `flavors.gradle` from Groovy to Kotlin DSL or removing `pre` / `pro` product flavors.
* Migrating `:data` from `java-library` to `com.android.library` (deferred to data-layer slices).
* Changing `AppProvideModule.kt`, `APIKeyInterceptor.kt`, `CityRoomDataSource.kt`, or `CityMapper.kt` runtime networking logic or moving non-secret URL constants (`API_WB_BASE`, `OPEN_WEATHER_ICON_URL`, `APP_ID_PARAM`).
* Modifying `google-services.json`, Firebase Auth, Firebase Remote Config, or any UI screen / Design System component code.
* Removing legacy `ui/theme/` files or rewriting Git history to purge previously committed keys.

### Job Story
When building or running CI on `MeteoMartoCompose` from a clean clone or Pull Request,
I want OpenWeather credentials to be injected declaratively via `secrets-gradle-plugin` with committed placeholder defaults, all modules compiled uniformly on JVM 21, and Design System CI watching the real `ui/designsystem` paths,
so I can prevent secret exposure, avoid mixed-JVM build drift, and ensure visual regression and styleguide CI actually trigger on Design System changes.

### Acceptance Scenarios

#### Scenario 1: Clean CI / Fresh-Clone Build Without API Key in `local.properties`
* **Given** `flavors.gradle` contains no `API_KEY_VALUE` field, `local.defaults.properties` defines `API_KEY_VALUE=DEFAULT_OPENWEATHER_API_KEY`, and `local.properties` does not define `API_KEY_VALUE` (or only defines `sdk.dir`)
* **When** `./gradlew assemblePreDebug` and `./gradlew testPreDebugUnitTest lintPreDebug --parallel --build-cache --configuration-cache` execute on JDK 21
* **Then** Gradle resolves `secrets-gradle-plugin:2.0.1` from `libs.versions.toml`, generates `BuildConfig.API_KEY_VALUE == "DEFAULT_OPENWEATHER_API_KEY"` without exposing `sdk.dir` in `BuildConfig`, and both build and canonical verification gate pass cleanly.

#### Scenario 2: Local Developer Override in Git-Ignored `local.properties`
* **Given** a developer adds `API_KEY_VALUE=<local_openweather_key>` to their git-ignored `local.properties`
* **When** the `:app` module generates `BuildConfig` for `preDebug` or `proDebug`
* **Then** `secrets-gradle-plugin` overrides the default value with the local key for `APIKeyInterceptor`, while `git status` keeps `local.properties` untracked and ignored.

#### Scenario 3: Design System CI & Dokka Path Alignment
* **Given** `.github/workflows/design-system-ci.yml` and the Dokka `-PdesignSystemDocs` task in `app/build.gradle.kts`
* **When** a change touches any file under `app/src/main/java/com/martorell/albert/meteomartocompose/ui/designsystem/**`
* **Then** both `push` and `pull_request` workflow path filters match `ui/designsystem/**` (with zero references to non-existent `ui/components/designsystem/**`), and `:app:dokkaGenerateHtml -PgenerateDocs -PdesignSystemDocs --no-daemon` includes `ui.designsystem.*` packages instead of suppressing them.

#### Scenario 4: Uniform JVM 21 Alignment Across All Modules
* **Given** `:domain`, `:usecases`, `:data`, and `:app` Gradle build files
* **When** Gradle compiles and runs unit tests across all modules under JDK 21
* **Then** all four modules target `JavaVersion.VERSION_21` and `JvmTarget.JVM_21` / `jvmToolchain(21)` with zero JVM target mismatch warnings or compilation errors.
