## 2. Goal, Non-Goals & Acceptance Scenarios

### Goal
Establish the deterministic visual foundation of `MeteoMartoCompose` under `com.martorell.albert.meteomartocompose.ui.designsystem.foundation` so all downstream component alignment and screen overhaul slices consume a single authoritative set of tokens: the 5 KISS weather palettes (`DayBaseline`, `Sunny`, `Rain`, `Night`, `ExtremeAlert`) with strict precedence resolution, WCAG-verified semantic colors, `Roboto Flex` variable typography with zero text sizes below `12.sp`, `DESIGN.md` shape tokens, and the 3 bundled `.webp` graphic drawables (`ic_logo.webp`, `ic_warning.webp`, `ic_error_forecast.webp`).

* Do **NOT** rebuild application screens (`Splash`, `Login`, `SignUp`, `Terms`, `CityForecast`, `Favorites`, `HighTemperatureAlert`) or wire live `CityWeatherDomain` telemetry into `CityWeatherScreen` (owned by downstream screen slices).
* Do **NOT** convert any full-screen layout mockups under `docs/ui/screens/` into Android drawables (`CONSTRAINTS.md` #17).
* Do **NOT** remove `app/src/main/res/drawable/ic_splash.xml` or refactor legacy `ui/theme/`.
* Do **NOT** add Robolectric functional tests, `MockK`, or `src/androidTest/` dependencies.

### Job Story
When building or rendering any MeteoMarto Design System component or weather screen,
I want the theme foundation to resolve the 5 KISS climate palettes deterministically, enforce `Roboto Flex` `>= 12.sp` typography and `DESIGN.md` shapes, and expose the bundled WebP graphic drawables,
so every static and dynamic screen shares an accessible, contrast-safe, and visually consistent foundation without hardcoded colors, sub-12sp labels, or wallpaper theme overrides.
