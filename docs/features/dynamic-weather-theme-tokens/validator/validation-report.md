### 2.2 Non-Blocking Code Review Observations (Low / Spec-Smells / Cross-OS Risks)

* **Observation 1 (`FndColorPrimitives.kt#L6-L49` & `FndColors.kt#L164-L198` — Semantic-Role Primitive Naming Cross-Reuse)**: To guarantee zero duplicate hex constants across `FndColorPrimitives`, several palette/role-named primitives are reused in semantically different slots (e.g., `ErrorContainerLight` `#FFDAD6` is used for `NightFndColors.onErrorContainer`, `ExtremeAlertFndColors.secondary`, and `ExtremeAlertFndColors.error`; `ErrorDark` `#FFB4AB` is used for `ExtremeAlertFndColors.hot`; `DayBaselineOnSurface` `#1A1C1E` is used for `ExtremeAlertFndColors.onPrimary`; `NightBackground` `#0E1419` is used for `NightFndColors.onPrimary`/`onSecondary`). This strictly satisfies `pr-review.md` Finding 2 (zero duplicate hexes, clear single-source table) and is non-blocking; if the token table expands in `design-system-components-alignment`, adopting neutral hue/tone reference names (e.g., `Rose90`, `Coral80`, `Slate900`, `Periwinkle80`) would decouple raw reference primitives from semantic roles.
* **Observation 2 (`FndColors.kt#L55-L62` & `FndColorPrimitives.kt` — Deferred KDoc Handoff)**: Per `pr-review.md` Finding 1 & Finding 2, `FndColors.Companion.fromPalette` retains its pre-Round-#1 verbose KDoc and `FndColorPrimitives.kt` has `0` KDoc by design so `workflow-documenter` can author both cleanly immediately after validator `accept`.
* **Observation 3 (`app/src/main/res/drawable/ic_{logo,warning,error_forecast}.webp` & `lint-results-preDebug.xml`)**: Independent inspection of `app/build/reports/lint-results-preDebug.xml` confirmed `0` warnings on all 9 modified/new `.kt` files (`FndColorPrimitives.kt`, `WeatherPalette.kt`, `FndColors.kt`, `FndTypography.kt`, `FndShapes.kt`, `DesignSystem.kt`, `MeteoMartoComposeLayout.kt`, `WeatherThemePaletteTest.kt`, `DesignSystemResourcesTest.kt`), and the same `6` spec-mandated warnings on the 3 `.webp` resources (`3x UnusedResources` transient until downstream screen slices consume `R.drawable.ic_*`; `3x IconLocation` because `CONSTRAINTS.md` #17, `DESIGN.md`, and `spec.md` Scenario 4 require `res/drawable/`). Consider evaluating `res/drawable-nodpi/` in a follow-up if RAM upscaling on `xxhdpi`/`xxxhdpi` becomes relevant.
* **Observation 4 (`DesignSystem.kt#L100-L130` & Live Emulator Visual Inspection)**: `lightColorScheme`/`darkColorScheme` map the 12 core roles specified in `spec.md` §6, leaving Material 3 container roles (`primaryContainer`, `secondaryContainer`, `surfaceContainer*`) at M3's default lavender tones (visible on the live emulator FAB and bottom navigation indicator). Downstream `design-system-components-alignment` should align M3 container tokens to eliminate residual lavender tinting.
* **Observation 5 (`FndColors.kt#L53,L72-L88`)**: In `buildCustomFndColors(palette)`, `resolvedOnPrimary` uses `palette.primary.luminance() >= LIGHT_LUMINANCE_THRESHOLD` (`0.5f`), whereas W3C equal-contrast white-vs-dark ink crossover is `~0.179f`. All 5 canonical palettes bypass this fallback and pass `>= 5.87:1`; if custom runtime palettes are introduced later, using contrast comparison or a `0.179f` threshold for `onPrimary` would harden mid-luminance primaries.
* **Observation 6 (`FndColors.kt` Thermal & Primary Contrast Against `background` vs `surface`)**: Carried forward from Iteration 1 for downstream slices: keep thermal telemetry text on `surface` cards (`>= 4.60:1`) rather than bare `background` (`4.37:1`–`4.40:1` on `DayBaseline`/`Sunny`/`Rain`), and provide an accessible text/tonal treatment for `SunnyPalette.primary` (`#E68A00`) on `#FFFFFF` surfaces in `design-system-components-alignment`.
