## 2. Findings

### 2.1 Blocking Findings (Critical / High / Medium)

### 2.2 Non-Blocking Code Review Observations (Low / Spec-Smells / Cross-OS Risks)

* **Observation 1 (`app/src/main/res/drawable/ic_{logo,warning,error_forecast}.webp` & `lint-results-preDebug.xml`)**: Independent inspection of `app/build/reports/lint-results-preDebug.xml` surfaced `0` warnings on all 8 modified/new `.kt` files, but `6` warnings on the 3 new `.webp` resources: `3x UnusedResources` (expected and transient — downstream screen slices `auth-splash-login-overhaul`, `city-forecast-dynamic-screen`, and `high-temp-alert-screen-overhaul` will consume `R.drawable.ic_*`) and `3x IconLocation` (`Found bitmap drawable res/drawable/ic_*.webp in densityless folder`). Placement in `app/src/main/res/drawable/` is explicitly required by `CONSTRAINTS.md` #17, `DESIGN.md` (Android Resource Conversion Policy), `design-system-governance` §3, and `spec.md` Acceptance Scenario 4, so this is non-blocking. However, Android treats `res/drawable/` as `mdpi` (`1x`), which causes `BitmapFactory` to upscale bitmap drawables `3x–4x` in RAM on `xxhdpi`/`xxxhdpi` devices; consider whether to migrate raster `.webp` illustrations to `app/src/main/res/drawable-nodpi/` (and update `CONSTRAINTS.md` #17 + `DESIGN.md`) during PR review or downstream screen wiring.
* **Observation 2 (`DesignSystem.kt#L67-L97` & Roborazzi / Emulator Visual Inspection)**: `lightColorScheme(...)` and `darkColorScheme(...)` map the 12 core roles specified in `spec.md` §6 (`primary`, `onPrimary`, `secondary`, `onSecondary`, `background`, `onBackground`, `surface`, `onSurface`, `error`, `onError`, `errorContainer`, `onErrorContainer`), leaving Material 3 container roles (`primaryContainer`, `secondaryContainer`, `surfaceContainer`, `surfaceContainerHigh`, `surfaceVariant`) at Compose Material 3's default lavender tones (`#EADDFF` / `#E8DEF8` / `#F3EDF7`). This is visibly reflected in the refreshed `MmButtonStatesPreview` (`Secondary Enabled`), `MmDialogPreview` (`Confirm` tonal button), `MmNavigationPreview` (bottom bar), and the live emulator FAB/navigation bar. Downstream `design-system-components-alignment` should derive neutral/palette-aligned `primaryContainer`, `secondaryContainer`, and `surfaceContainer*` tokens in `DesignSystem.kt` (or component defaults) to eliminate residual M3 lavender tinting.
* **Observation 3 (`FndColors.kt#L28,L39-L55`)**: In `buildCustomFndColors(palette)`, `resolvedOnPrimary` uses `palette.primary.luminance() >= LIGHT_LUMINANCE_THRESHOLD` (`0.5f`). While all 5 canonical palettes bypass this fallback and achieve `>= 5.87:1` `onPrimary/primary`, the W3C equal-contrast crossover between white and black ink is `~0.179f` (e.g., `SunnyPalette.primary = #E68A00` has luminance `~0.350`, where white yields `2.63:1` and dark ink yields `5.87:1`). If custom palettes are ever passed at runtime, comparing actual contrast against `Color.White` vs `DayBaselinePalette.onSurface` (or using a `0.179f` luminance threshold for `onPrimary`) would guarantee WCAG AA for mid-luminance primaries too.
* **Observation 4 (`FndColors.kt` Thermal & Primary Contrast Against `background` vs `surface`)**: Adversarial W3C contrast calculation across all 13 role pairs x 5 palettes confirmed all `spec.md` pairs (`onSurface/background`, `onSurface/surface`, `onPrimary/primary`, `onSecondary/secondary`, `onError/error`, `onErrorContainer/errorContainer`, `onSuccess/success`, `error/surface`, `hot/surface`, `cold/surface`) pass `>= 4.5:1`. Note for downstream component/screen slices (`design-system-components-alignment`, `city-forecast-dynamic-screen`): (a) `cold` on `DayBaseline`/`Sunny` `background` is `4.37:1` and `hot` on `Rain` `background` is `4.40:1`, so thermal telemetry text must always render on `surface` cards (`>= 4.60:1`) rather than bare `background`; (b) `SunnyPalette.primary` (`#E68A00`, mandated by `DESIGN.md`) on `#FFFFFF` `surface` is `2.63:1`, so tertiary/text buttons on `Sunny` screens will need an accessible darkened amber text color or tonal treatment in `design-system-components-alignment`.
* **Observation 5 (`WeatherThemePaletteTest.kt#L140-L200`)**: Test #2 verifies `RobotoFlex` identity, `>= 12.sp`, `lineHeight >= fontSize`, and exact `FndTypography <-> MaterialTheme.typography` parity across all 15 scales, but does not assert that `RobotoFlex` registers all 4 variable weights (`Normal`, `Medium`, `SemiBold`, `Bold`) on `(RobotoFlex as FontListFontFamily).fonts`. Verified directly in `FndTypography.kt#L30-L35`; optional hardening if desired later.
* **Observation 6 (Live Emulator OS Dark Mode Status Bar Icons)**: During Level 4 runtime probing with `cmd uimode night yes`, `MeteoMartoComposeLayout` correctly stayed pinned to light `DayBaselinePalette`, while the Android system status bar switched to light icons (becoming invisible against `#F8F9FA`). Expected until `edge-to-edge` / `navigation-shell-unification` synchronizes `WindowInsetsController.isAppearanceLightStatusBars` with `MeteoMartoTheme.colors.isLight`.
