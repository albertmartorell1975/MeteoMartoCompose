## 2. Goal, Non-Goals & Acceptance Scenarios

### Goal
Establish a clean, lifecycle-safe, type-safe Navigation Compose shell in `com.martorell.albert.meteomartocompose.ui.navigation` where `@Stable AppState` owns intent-driven navigation and adaptive `WindowSizeClass`, `AppShellState` deterministically maps the active backstack entry (`NavBackStackEntry?`) to immutable `AppShellChrome` and tab-selection state, `TopAppBarCustom` is completely stateless and decoupled from `AppState` and `hiltViewModel`, `Navigation.kt` collects root state with `collectAsStateWithLifecycle()`, duplicate `DashboardScreens.Favorites` registration is eliminated, and `DashboardScreens.CityForecast(cityName: String? = null)` serves as the single unified route contract for both current-location weather and favorite-city detail.

### Non-Goals
* **No Navigation 3 migration:** Retain stable Jetpack Navigation Compose (`2.9.3`) with Kotlinx Serialization type-safe routes per `docs/build-brief.md` and `feature_list.json`.
* **No `MainActivity.kt` or `AndroidManifest.xml` changes:** Edge-to-edge Activity/Manifest configuration (`adjustResize`, `isNavigationBarContrastEnforced`) is deferred to `auth-splash-overhaul`, and warm `singleTop` `onNewIntent` (`handleDeepLink`) handling is deferred to `high-temp-alert-screen-overhaul`.
* **No `FabState.kt` or `FabCustom.kt` rewrite/deletion:** Preserve `ui/FabState.kt` and `ui/navigation/shared/FabCustom.kt` untouched; `AppState` retains `FabState` delegation verbatim (deferred to `city-forecast-screen-and-error-ui`).
* **No screen visual/Stitch layout overhauls:** Do NOT modify `SplashUI`, `LoginScreen`, `SignUpScreen`, `TermsScreen`, `CityWeatherScreen`, `FavoritesScreen`, `FavoritesDetailScreen`, or `HighTemperatureAlertScreen`.
* **No ViewModel refactoring or unification:** Do NOT modify `MainViewModel`, `CityWeatherViewModel`, `FavoritesViewModel`, `FavoritesDetailViewModel`, `LoginViewModel`, `SignUpViewModel`, or `FndDesignSystemViewModel`.
* **No Design System (`Fnd*` / `Mm*`) component changes or Roborazzi snapshot regeneration:** `MmNavigation.kt` was already decoupled from `NavDestination` in PR #13 Review Round #1 (`isItemSelected: (MmNavigationItem) -> Boolean`); preserve all `60/60` Design System golden PNGs untouched.
* **No `:domain`, `:data`, `:usecases`, Room, API, or Gradle dependency changes.**

### Job Story
When an authenticated user navigates between Current Location weather, Favorites, Favorite City detail, and High-Temperature Alert routes across phones, tablets, configuration changes, and OS background kills,
I want a unified, lifecycle-aware, type-safe navigation shell with decoupled top-bar chrome and zero duplicate routes,
so that adaptive bottom-bar/rail switching, back navigation, logout, and process-death restoration behave predictably and downstream forecast unification can plug directly into `CityForecast`.

### Acceptance Scenarios

#### Scenario 1: Adaptive Top-Level Tab Switching & State Preservation (Compact & Expanded)
* **Given** an authenticated user lands on `SubGraphs.Dashboard` at `DashboardScreens.CityForecast(cityName = null)`
* **When** the user switches between the **City** and **Favorites** items on the compact bottom navigation bar (`< 600dp`) or expanded leading navigation rail (`>= 600dp`) — regardless of whether the session started logged-in or logged-in via `SubGraphs.Auth`
* **Then** `AppShellState` renders bottom/rail chrome with only the active tab selected, updates the TopAppBar title between `"Meteo Marto"` (`showLogoutAction = true`, `showBackButton = false`, FAB allowed) and `"List of Favorites"` (`showLogoutAction = false`, `showBackButton = false`, FAB hidden), preserves tab state without duplicating backstack entries, and resets any collapsed `TopAppBar` scroll offset on destination transitions.

#### Scenario 2: Unified `CityForecast` Route for Favorite Detail & Clean Back Navigation
* **Given** the user is on `DashboardScreens.Favorites` with at least one saved favorite city (e.g., `"Barcelona"`)
* **When** the user taps `"Barcelona"`
* **Then** `AppState.navigateToCityForecast("Barcelona")` navigates to `DashboardScreens.CityForecast(cityName = "Barcelona")` inside `SubGraphs.Dashboard` (with zero duplicate `DashboardScreens.Favorites` routes anywhere in the graph), `FavoritesDetailViewModel` receives `"Barcelona"` via `SavedStateHandle["cityName"]`, `AppShellState` switches chrome to Favorite Detail mode (`showBottomNavigation = false`, `showTopAppBar = true`, title `"City weather"`, `showBackButton = true`, `showLogoutAction = false`, `showFavoriteFab = false`), and tapping either the TopAppBar Back button or system Back pops cleanly back to `DashboardScreens.Favorites`.

#### Scenario 3: Decoupled TopAppBar Logout & Preserved Favorite FAB Gating
* **Given** the user is on `DashboardScreens.CityForecast(cityName = null)` with loaded current-location weather
* **When** the user taps the TopAppBar Logout icon (or switches between `CityForecast(null)`, `Favorites`, and `CityForecast("Barcelona")` to observe Favorite FAB visibility)
* **Then** the decoupled stateless `TopAppBarCustom` invokes its `onLogoutClick` callback (zero `hiltViewModel` inside `TopAppBarCustom`) wired from the single `dashboardViewModel` resolved in `Navigation.kt` to open the logout confirmation dialog; confirming logout calls `AppState.navigateToAuth()`, clears `SubGraphs.Dashboard` (`inclusive = true`), destroys the Dashboard-scoped `CityWeatherViewModel`, and hides all dashboard chrome on `AuthScreens.Login`; meanwhile the existing `FabState`-backed Favorite FAB continues to render only on `CityForecast(null)` when `shellChrome.showFavoriteFab && appState.isFabVisible && dashboardViewModel != null` with zero behavioral regression.

#### Scenario 4: Process Death Restoration on Unified Detail Route & Cold Alert Deep-Link Preservation
* **Given** the app is open on `DashboardScreens.CityForecast(cityName = "Barcelona")` (or cold-launched with the existing `meteomarto://alert/high-temperature/38.5` deep link)
* **When** an Activity recreation or OS LMK process death occurs while on `CityForecast(cityName = "Barcelona")`, or the app is cold-launched into `DashboardScreens.HighTemperatureAlert` via `navDeepLink`
* **Then** `CityForecast(cityName = "Barcelona")` restores directly onto the top of the backstack with its ID-only `cityName` argument intact in `SavedStateHandle`, restores Detail chrome (Back arrow, `"City weather"` title, no bottom bar/rail), reloads `"Barcelona"`, and pops cleanly to `Favorites` on Back; cold alert deep links continue to resolve `DashboardScreens.HighTemperatureAlert(temperature)` inside `HomeNavGraph.kt` without bottom-bar or TopAppBar bleed-through, dismissing cleanly via `appState.navigateUp()`.
